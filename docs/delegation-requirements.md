# 遠端交辦需求訪談

狀態：產品需求與整體理解已由使用者確認；作為技術設計基線，不代表已實作或已驗證。

## 已確認需求（2026-09-12）

- 排程巡查 issue 後交辦、AI Agent 透過 MCP 交辦、LINE／Telegram 等聊天入口，共用同一套任務核心。
- 第一個完整跑通的情境是 MCP 交辦並取得結果。
- 交辦方是具備 MCP 呼叫能力的 AI Agent；Grok bot 僅為例子，不是指定整合對象或必要驗收產品。首版不依賴 Grok 專屬介面。
- 產品須允許執行端推送分支及建立 PR；是否建立 PR 依任務要求，並非所有任務的必要產出。此需求不構成本次訪談的 GitHub 寫入授權。
- 交辦方負責挑選工作、整理指令與指定 Agent；AgentPort 負責執行與追蹤。
- 第一階段先做 MCP，A2A 延後。
- 長任務先回傳任務 ID，再查詢狀態與結果；交辦方離線不應中止工作，重新連線後仍可查詢。服務重啟後也須保留任務紀錄與最後已知狀態。
- 第一階段限本人與明確授權的自有 bot 使用；主機權限採下述專用服務帳號模式。
- 未指定交付方式時，預設修改、測試並回報；推送與建立 PR 依任務要求或事先設定的專案規則。
- 支援需要澄清時等待回答、繼續同一任務；預設等待 24 小時，可依任務調整，不計入實際執行期限。到期停止任務並暫停相關後續要求，保留問題與既有產出。
- 執行中收到一般追加要求先排隊；澄清回答送到對應等待點；明確停止指令走外側取消。接收時回報已排隊、已送達或停止中，不把接收視為已執行。
- 「好了沒」直接查外側狀態，不排入 Runtime 工作佇列。分開呈現程序存活、工作進展及目前可否觀察的證據。
- 交辦方理解自然語言，呼叫明確的查詢、追加或取消操作；核心不另設模型猜測意圖。聊天入口需保留直接查詢與停止操作，避免受交辦方模型忙碌影響。
- 無新進展先標示疑似停滯，回報最後活動與可確認的執行情況；達任務設定的最長期限才自動停止。確認程序死亡則回報異常，不能因安靜就宣告死亡。
- 服務重啟後核對執行情況；無法確認時明示執行結果未知，不自動重跑。服務無法連線時，由外部入口明確回報，不把舊快照當成目前正常狀態。
- 前項失敗或取消時，同一工作脈絡的後續要求暫停，交辦方決定繼續、修改或取消。
- 一般追加要求建立獨立、可追蹤及取消的新 Task，沿用同一 Context 並依序執行；澄清回答屬於原 Task。
- 尚未開始的 Task 可明確修改或取消；開始後的追加要求另行排隊，不依訊息先後猜測覆蓋關係。
- 互動能力依 Runtime 實際支援限制；不支援往返時明確回報。執行中遇到未預期、無法處理的互動需求，保留問題與產出，結束本次執行，不假裝仍能等待並繼續。
- 首個 Claude Code／Linux 整合必須通過提問、回答、繼續同一 Task 的正向往返驗收；回報不支援不能視為首版完成。其他尚未具備此能力的整合仍須明確揭露限制。
- 每個待回答問題有獨立識別，只採用第一個有效回答；後到的不同答案回報衝突，相同回答重送不重複啟動。修改已採用答案須明確追加指令或取消，不直接覆蓋。
- 外側查詢正常情況以 2 秒內回傳為驗收目標，包含狀態、最後進展時間、觀察時間與待回答問題；入口超過 5 秒連不上服務就回報無法取得最新狀態。數值是待驗證目標，不是已達成效能。
- 核心保存可查詢事件，由交辦方或聊天入口負責完成、待回答及疑似停滯通知；查詢結果不依賴通知是否送達。
- 平台順序：第一階段 Linux，第二階段 macOS；第一個驗證的 Runtime 為 Claude Code。
- 預設累計執行期限 60 分鐘，排隊與等待回答不計入；任務可另設期限。連續 10 分鐘無可觀察進展提示疑似停滯，並明示是否仍有工具執行中；初值後續以實測調整。
- 重啟後保留尚未開始的佇列，但先暫停，待交辦方確認；先前執行中或等待回答的任務也先核對，不自動重送給 Runtime。
- 首版同一 Workspace 一次一項工作，等待回答期間也不放行其他修改；不同 Workspace 可以並行。取消等待中的任務須先確認執行已停止，再解除占用。
- 本人與明確授權的自有 bot 可共用工作存取範圍，能跨入口回答、修改佇列或取消；保留各自身分與操作紀錄。澄清回答不等於授予新權限，超出既定執行權限的要求另行處理。
- 任務結果、問題與操作紀錄預設保留 30 天，可由管理者調整；未結束、暫停或停止未確認的任務不因期限刪除。完整 Runtime 原生對話紀錄另依執行工具政策管理。
- 首版由管理者預先設定 Agent、Workspace 與 Runtime；交辦方選 Agent，不直接指定任意 repo 或主機路徑。
- 首版使用專用服務帳號的權限，Workspace 僅為工作目錄，不提供各 Agent 之間的檔案與憑證硬隔離。可用憑證與執行權限由管理者預設；超出權限時明確回報，不透過一般澄清回答提權。
- 完成結果包含摘要、變更檔案清單、檢查結果、未完成事項及實際產生的 commit／分支／PR 資訊；分析或除錯任務可以沒有程式變更。首版不提供任意工作目錄檔案下載。
- 第一階段以 MCP 驗收交辦、排隊、查詢、回答、取消及重啟後查詢，包含 Runtime 卡住時仍可查詢與發出取消並觀察停止結果；排程、LINE／Telegram 留待後續入口整合。

架構取捨見 [外側觀察與控制](adr/0001-external-observation-and-control.md)及[跨重啟保留任務紀錄](adr/0002-task-records-survive-restart.md)。

## 與現有設計的關係

本輪 technical-design.md 已依需求基線改為 MCP 優先、A2A 延後；architecture-candidates.md 標記為歷史探索文件。

舊設計的忙碌即拒絕及不支援等待輸入，已由佇列、問題回覆與外側控制契約取代。

舊設計的記憶體狀態改為持久任務／receipt／事件；保留紀錄不等於自動恢復執行。

執行期限、30 天保存、共享 scope／個別 actor、Linux 首版與 macOS 第二階段已納入新版設計；macOS 的停止與清理機制尚未驗證。

## 已確認行為的驗收情境

以下為未執行的驗收要求，不是測試結果。

| 情境 | 可觀察結果 |
| --- | --- |
| 具 MCP 呼叫能力的交辦方提交長任務後斷線 | 先取得 Task ID；工作不因斷線取消，再連線可查狀態與結果；不要求特定品牌的交辦方 |
| Claude Code 忙碌或卡住時查詢 | 查詢不進 Runtime 佇列，依回應目標回傳觀察證據或無法取得最新狀態 |
| 執行中追加要求 | 新 Task 立即可追蹤，在同 Context 排隊；接收不等於執行 |
| 尚未開始的 Task 修改或取消 | 明確操作該 Task，不依訊息順序猜測覆蓋；開始後不能當作尚未開始修改 |
| Claude Code 執行遇到澄清問題 | 必須實際完成提問、回答與繼續原 Task；等待有期限，同 Workspace 不啟動其他工作，不能以不支援略過 |
| 本人與 bot 同時或重複回答 | 問題識別對應正確 Task；首個有效回答生效，重送不重複啟動，不同的後到答案回報衝突 |
| 執行中取消或達期限 | 外側操作可回應；只有確認停止後才解除 Workspace 占用，相關後續要求暫停 |
| 安靜、程序死亡與觀察失聯 | 三者分別呈現；沒有輸出不等於死亡，無法確認不宣告成功 |
| 服務重啟 | 原 Task ID 可查最後已知紀錄；執行先核對，佇列暫停，不自動重跑 |
| 任務完成但通知未送達 | 最終結果及事件仍可查詢；是否推送或開 PR 依任務／專案規則 |

## 後續技術設計與驗證門檻

下列項目已於 Technical Design 具體化，仍須固定版本與實作驗證，不能把設計當作通過驗收。若技術驗證要求改變已確認的產品行為，須再討論。

- MCP 連線、認證及操作契約：以通用 MCP 交辦方為目標，驗證相容性，不假設任意 Client 都支援全部協定能力。
- Task 狀態與合法操作：定義排隊、執行、等待回答、暫停、停止中、終態及恢復核對；將疑似停滯、觀察失聯與執行結果未知分清楚，不用程序存活推論成功。停止未確認時不能釋放 Workspace。
- 佇列容量及跨 Context 排序；問題識別、回答競爭與重送的原子處理；修改與開始執行競爭時的明確結果。
- 共享授權範圍內的人與 bot 身分、操作紀錄、通知追蹤及超出既定執行權限時的結果。
- 持久化、去重、30 天紀錄保存及重啟核對方式；核對完成前不自動重送工作。
- 固定版本的 Claude Code 整合能力與 Linux 執行資源控制；正向澄清往返、外側查詢回應目標及可靠停止均需實際驗證。macOS 於第二階段另行驗證。
