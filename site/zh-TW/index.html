運作模型

單一 registry 即為權限的來源。

workspace

每個 Logical Agent 都綁定至管理員選定的工作目錄。

runtime

Claude Code 或 Codex 由 host 設定選擇，而不是由 Caller 選擇。

policy

每個 Task 都以明確的唯讀、workspace-write 或 full policy 執行。

使用情境

在工作需要時，啟動本機 coding runtime。

Caller 選擇預先設定的 Logical Agent。AgentPort 為 Task 啟動綁定的 Runtime、讓進度可觀察，並讓 host 的 Git 與 GitHub 決策保持明確。

01 / IMPLEMENT

將已核准的 issue 交給已準備好的 workspace。

workspace-write Agent 可接收 issue 與驗收條件作為 Task，並在設定好的 workspace 內實作和測試。更新 main、建立 worktree 或 branch，以及開啟 pull request，仍是 Git 與 host runtime 的操作——不是 AgentPort 的控制項。

submit_task → get_task
02 / TRIAGE

在授與寫入權限前先排查 issue。

唯讀 Agent 可檢查設定好的 workspace、測試，以及 Task 中附帶的 issue context。只有 Runtime 具備授權的 host 工具與網路存取時，才能查詢最新 GitHub issue；AgentPort 不提供 issue API。

list_agents → submit_task
03 / SUPERVISE

無須永久開著 coding session，也能看見長時間工作。

可 long-poll Task 的狀態變化、檢查最終回覆與 Git 摘要、在相同 Context 發送 Follow-up Task，或在工作應停止時請求取消。

get_task → follow_up → cancel_task

AgentPort 負責：設定好的 Agents、policies、Task state、Context、排隊與結果。

Runtime 與 host 負責：Git worktree 與 branch、GitHub issue 與 pull-request 存取、憑證以及定時觸發。

精簡的 protocol surface

六個 MCP tools，涵蓋完整的 Task lifecycle。

01 / DISCOVER

列出 Agents

派送工作前，檢查已設定的 Logical Agents 與其 policies。

02 / DISPATCH

提交並追問

建立 Task；當 Runtime 提問時，延續同一個 Context。

03 / OBSERVE

等待、檢查、取消

long-poll Task state、查看最終回覆與 Git 摘要，或安全地取消。
